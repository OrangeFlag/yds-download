# yds-download

Последовательное скачивание курсов из публичной папки Яндекс Диска. Год и названия курсов берутся из самой папки. По умолчанию скачиваются **все курсы** — включая AI/ML, если они есть в источнике.

Внутри курса одновременно скачиваются до 2 файлов, до 4 соединений на файл, без ограничения скорости. Следующий курс начинается после завершения всех попыток предыдущего. Файлы упорядочены по размеру, от меньших к большим. Полная загрузка канала зависит также от ограничений Яндекса и сети.

## Быстрый запуск

Нужны Linux, Python **3.11+**, `aria2c`, `cp` (coreutils) и пользовательский systemd для фонового запуска. Python использует только стандартную библиотеку. OAuth, rclone и WebDAV для публичных папок не требуются.

Установка зависимостей, если их нет:

```bash
# Fedora
sudo dnf install python3 aria2 coreutils git
# Debian/Ubuntu: Python должен быть версии 3.11 или новее
sudo apt install python3 aria2 coreutils git
```

### Получить каталог и выбрать курсы

```bash
cd ~/gitRepos/yds-download
python3 download.py catalog \
  --source 'https://disk.yandex.ru/d/2cjhoac1AX0PMw' \
  --output catalog.json
${EDITOR:-nano} catalog.json
```

Пример структуры:

```json
{
  "source": "https://disk.yandex.ru/d/2cjhoac1AX0PMw",
  "title": "ШАД весна 2026",
  "courses": [
    {"name": "Компьютерные сети", "enabled": true, "url": "..."},
    {"name": "Другой курс", "enabled": false, "url": "..."}
  ]
}
```

Это иллюстрация структуры: используйте реальные названия из сгенерированного каталога. Установите `enabled: false` для ненужных курсов. Переставьте объекты в массиве `courses`, чтобы изменить порядок. Поле `url` оставлено для просмотра; загрузка использует `source` и `name`. Не меняйте названия курсов. Для другого года выполните `catalog` с его ссылкой и создайте отдельную папку назначения.

```bash
YDS_DEST='/run/media/geerkics/088d300e-87f5-4293-999d-80726a0b2250/YandexDisk/ШАД весна 2026'
# Убедитесь, что внешний диск смонтирован, прежде чем создавать папку.
mkdir -p "$YDS_DEST"
./start.sh "$YDS_DEST" --catalog "$PWD/catalog.json"
```

`examples/infra-2026.json` воспроизводит нашу выборку из 12 инфраструктурных курсов и курсов программирования, начиная с компьютерных сетей:

```bash
./start.sh "$YDS_DEST" --catalog "$PWD/examples/infra-2026.json"
```

### Скачать всё или отобрать курсами в командной строке

Для всех курсов редактируемый каталог не обязателен:

```bash
./start.sh "$YDS_DEST" --source 'https://disk.yandex.ru/d/2cjhoac1AX0PMw'
```

Или выбрать конкретные названия:

```bash
./start.sh "$YDS_DEST" --source 'https://disk.yandex.ru/d/2cjhoac1AX0PMw' \
  --include 'Компьютерные сети' --include 'Базы данных, часть 2'
```

Или исключить конкретный курс:

```bash
./start.sh "$YDS_DEST" --source 'https://disk.yandex.ru/d/2cjhoac1AX0PMw' \
  --exclude 'Машинное обучение, часть 2'
```

`--include` и `--exclude` можно повторять и использовать вместе с `--catalog`. Явный `--include` заменяет выбор по `enabled`; `--exclude` применяется последним. Порядок всегда определяется каталогом, при прямом запуске — списком Яндекса. Неизвестные названия вызывают ошибку. Автоматического определения «AI», «ML» или «инфраструктуры» нет: названия и состав меняются по годам.

Без systemd можно запускать в терминале:

```bash
python3 -u download.py download --catalog catalog.json --destination "$YDS_DEST"
```

## Наблюдение, остановка, продолжение

### Все фоновые сервисы: один конфиг

Рабочие параметры машины Walterit сохранены в
[`deploy/services.walterit.json`](deploy/services.walterit.json): цели 90 Мбит/с
в обе стороны, актуальная точка монтирования, прокси и лимиты. Ссылки доступа к
Nextcloud заменены на `READ_SHARE`/`UPLOAD_SHARE`; действующие ссылки находятся
только в приватном `~/.config/yds-download/services.json`.

`services.py` управляет очередью скачивания, Range и отправкой в Nextcloud/OpenCloud.
Нужен пользовательский systemd; `sudo` не требуется.

```bash
mkdir -p ~/.config/yds-download
cp examples/services.json ~/.config/yds-download/services.json
chmod 600 ~/.config/yds-download/services.json
${EDITOR:-nano} ~/.config/yds-download/services.json

./services.py up                 # запустить все настроенные сервисы
./services.py down               # остановить все и сохранить прогресс
./services.py restart            # применить изменения конфига
./services.py status             # состояния и пути к логам
./services.py stats              # все сохранившиеся сервисные логи, включая ротации
./services.py stats --since 1h   # статистика за час; также 15m, 2d
./services.py up queue range     # только скачивание и восстановление
./services.py down nextcloud opencloud
```

Конфиг читается при каждом вызове; другой файл выбирается через
`./services.py --config /path/services.json status`. Настоящий конфиг храните вне
репозитория. В примере замените пути, UUID, ссылки облаков, имя пользователя и путь
к файлу токена. Каталоги и очереди должны быть подготовлены заранее.

В одном JSON находятся `repo`, `state_dir`, `mount_root`, `disk_uuid`, переменные
окружения (включая прокси), параметры команд, `queue_tuning` и лимиты systemd.
`speed_targets_mbit_s: {"download": 90, "upload": 90}` задаёт отдельные цели
автоподбора для общего бюджета скачивания и общего бюджета отправки в оба облака.
90 Мбит/с = 11 250 000 байт/с. На достигнутой цели контроллер сохраняет число
файлов; при снижении скорости снова пробует увеличить параллельность в заданных
границах. Это цель по подтверждённым байтам, а не ограничитель всего сетевого
трафика: Range-запросы, повторы и служебный обмен могут давать дополнительный трафик.
`0` или отсутствие цели оставляет прежний поиск максимальной скорости. Значение
передаётся worker через `YDS_TRANSFER_TARGET_MBIT_S`; у участников одного общего
бюджета оно должно совпадать. Смена цели требует общего `restart`.
`queue_tuning` заменяет общие `tuning` в `course_queue`, сохраняя задания, прогресс
и настройки отдельных архивов. Для его изменения остановите все сервисы или
вызовите общий `restart`. Очереди, каталоги и состояние каждого файла остаются
данными загрузчика: их не нужно переносить в конфиг управления сервисами.

В строках доступны `$repo`, `$state_dir`, `$mount_root`, `$home`; литеральный знак
доллара записывается как `$$`. Команды задаются массивами аргументов и запускаются
без shell. Общие `environment` и `properties` можно переопределить внутри сервиса.
Для отключения прокси задайте пустые значения его переменных, включая варианты
в нижнем регистре. Токены остаются в отдельных секретных файлах.

Перед стартом проверяются UUID и возможность записи на внешний диск. Новые записи `.download` сохраняют поле `local` относительно каталога
соответствующего архива; ссылки `destination`, `catalog` и `wait_for.destination`
в очереди — относительно самого файла очереди. При чтении поддерживаются
и новые относительные, и прежние абсолютные пути. Поэтому архив и очереди
можно перемонтировать без изменения новых ссылок. Абсолютные пути внешних
копий, находящихся за пределами архива, сохраняются, поскольку они могут
относиться к другим дискам. Путь `mount_root` в конфигурации сервисов —
подсказка для поиска диска по UUID, а не привязка записей состояния.

При смене
пути внесите прежние точки монтирования в `previous_mounts`: пути в JSON/JSONL
внутри `.download` будут перенесены существующим механизмом `storage.py`, только
при остановленных сервисах. Первый такой запуск может занять время на HDD;
данные видео не перемещаются. Защита от отключения диска остаётся включённой.
`down` и `status` не требуют доступного диска. Повторный `up` пропускает работающие
сервисы; при ошибке группового старта останавливаются только сервисы этого вызова.
Общий `down`/`restart` учитывает также сервисы, удалённые из конфига: оставшийся
работать worker не сможет незаметно мешать переносу состояния.

Логи по-прежнему ограничены по размеру и находятся в `state_dir`:

`stats` показывает завершения файлов, подтверждённые МБ и скорости по каждому
источнику/облаку, слоты передачи, очереди Range/Recheck/SHA, память cgroup с
разделением anon/cache, OOM, свободное место и ошибки за выбранный период.
Вывод разделён на таблицы передач, сервисов и памяти, очередей, сети и диска,
проблем и охвата журналов. Объёмы показаны в КБ/МБ/ГБ/ТБ, память — в МиБ,
скорость — в Мбит/с. Слоты одного источника суммируются; звёздочка возле них
означает устаревший снимок, «нет данных» отличается от измеренного нуля.
Без `--since` используется доступная история каждого неротированного и
сохранившегося ротированного лога, а не фиксированный час. Отчёт читает метаданные
и логи, без SHA-перечитывания видео и обхода всех задач. `TRANSFER STATS` — минутные
снимки общих счётчиков по источникам: закрытие участника не стирает его вклад;
перезапуск бюджета начинает новую эпоху. Неизвестные старые байты не выдаются за
ноль: объёмы обозначены `≥`, при отсутствии снимков используются только известные
приращения прогресса. Для скорости нужны два свежих снимка с интервалом от 30 с.
События завершения могут включать повторную передачу/проверку того же файла.
Служебный трафик, Range и непринятые сервером повторы в подтверждённые байты не входят.

```bash
tail -F ~/.local/state/yds-download/{queue,range,nextcloud,opencloud}.log
```

Это временные юниты systemd: автоматический старт при входе/перезагрузке не
включается. Старые ручные `systemd-run` и файлы с его аргументами больше не нужны.

```bash
tail -f "$YDS_DEST/.download/download.log"
systemctl --user status yds-download.service --no-pager
systemctl --user stop yds-download.service
```

`Ctrl+C` при просмотре `tail` закрывает только просмотр. Остановка службы отправляет SIGINT; aria2 сохраняет прогресс. Для продолжения повторите ту же команду `start.sh`. Служба независима от терминала; для работы после выхода из пользовательской сессии потребуется настроенный администратором linger. Автозапуск после перезагрузки не настроен: повторите запуск после монтирования диска. Завершившаяся служба удаляется (`--collect`), журналы остаются на диске.

Не запускайте два загрузчика для одной папки. Этот скрипт использует файловую блокировку. Если там уже работает старый скрипт из нашей сессии, сначала остановите его:

```bash
systemctl --user stop shad-infra-download-v3.service
```

Затем запускайте новую версию с **той же папкой назначения**: `.aria2` и готовые файлы будут использованы повторно. Старый скрипт не поддерживает новую блокировку.

## Что хранится в папке назначения

`.download/` содержит локальное состояние, журналы и временные ссылки. Эта папка исключена через `.gitignore` и не публикуется в Git.

| Файл / папка | Содержимое |
| --- | --- |
| `Порядок скачивания.txt` | Выбранные курсы по порядку, со ссылками |
| `.download/catalog.json` | Каталог, использованный в этом запуске |
| `.download/courses.json` | Фактический список выбранных курсов |
| `.download/download.log` | Общий журнал фонового запуска, скорость, прогресс, переходы между курсами |
| `.download/aria2.log` | Подробные ошибки HTTP и сообщения aria2 о загрузках |
| `.download/catalog-reports/` | Подробные отчёты по карточкам курсов; только локально |
| `.download/report-pending/` | Сохранённые задания обновления MD/commit/push; повторяются после ошибки и перезапуска |
| `.download/events.jsonl` | Результат каждого файла после каждой попытки обработки курса |
| `.download/NN-manifest.json` | Ожидаемые пути, размеры и SHA-256 файлов курса |
| `.download/NN-status.json` | Итог именно этого курса: `complete`, `total`, `verified`, `failed` |
| `.download/summary.json` | Общий итог текущего запуска |
| `.download/range-retry.json` | Результаты восстановления ранее неудачных файлов, обновляются после каждого файла |
| `.download/partial-copies.json` | Локальные пути частично доступных копий и процент подтверждённых байтов |
| `corrupted/failed.json` | Неудачи текущего/последнего завершённого запуска |
| `corrupted/ДАТА-ВРЕМЯ/` | Частичные/повреждённые файлы с `.aria2` и журнал неудач этого запуска |

Статусы файлов: `valid` — размер и SHA-256 совпали; `missing` — локального файла нет; `partial` — есть метаданные незавершённой загрузки; `invalid` — неверный размер или SHA-256. После передачи партии проверка идёт в фоне; до подтверждения SHA файл не считается исправным. Оперативные сообщения находятся в `aria2.log`.

### Фоновая проверка и восстановление

Обычный запуск имеет три очереди: передача файлов через aria2, проверка SHA и Range-восстановление. Партии курсов передаются в порядке каталога; следующий курс может скачиваться, пока предыдущий проверяется или восстанавливается. Готовые результаты SHA/Range обрабатываются каждые 5 секунд во время передачи: статусы и отметки завершённых курсов публикуются без ожидания всей партии. Оставшиеся обычные retry получают приоритет перед новым курсом. Архив/семестр заканчивается только после обработки всех фоновых задач.

Один работник проверяет SHA; полное восстановленное тело использует ту же блокировку хеширования. aria2 запускается без checksum, поэтому повторной проверки там нет. Range обрабатывает один файл за раз: при активной обычной передаче новые запросы ограничиваются одним параллельным потоком; ранее начатые запросы заканчиваются. В остальное время действует `--range-workers`. `--deep` остаётся отдельной явной проверкой; его запуск ждёт проверки файлов.

В `.download/tasks/*.json` сохраняются задачи и результаты, а `.download/transfer-state/XX/HASH.json` хранит номер попытки и продолжение передачи, проверки или восстановления (подробный `event` сохраняется только для незавершённых фаз). После SIGINT незавершённые задачи продолжаются при следующем запуске. Выполненное ограниченное восстановление не повторяется без `--retry-check`. Исходные тела, `.aria2` и `.ranges.json` сохраняются в `corrupted`; очередь остаётся приватной и не пушится.

В статусе курса `state: verifying` или `recovering` и `pending` означают, что обработка продолжается. `state: finished` появляется только после всех задач; `complete: true` требует SHA-подтверждения каждого оригинала. MD, коммит и push обновляются после завершения обработки курса.

**Курс полностью скачан**, если в его `NN-status.json` стоит `complete: true` и `verified` равен `total`. В общем журнале появляется `COURSE VERIFIED COMPLETE`. Если курс обработан, но есть неудачи, появляется `COURSE FINISHED WITH ERRORS` и `complete: false`. Обычный повторный запуск пропускает уже обработанный курс (`state: finished`), в том числе курс с исчерпанными попытками. `--deep` проверяет локальные файлы без скачивания и сохраняет состояние очереди. Номера `NN` соответствуют текущему выбранному порядку; при смене выборки старые файлы статуса могут остаться — сверяйте поле `course` и текущий `courses.json`.

```bash
rg 'COURSE VERIFIED COMPLETE|COURSE FINISHED WITH ERRORS|ALL SELECTED' \
  "$YDS_DEST/.download/download.log"
cat "$YDS_DEST/.download/01-status.json"
```

## Обрывы и недоступные файлы

`--retries N` задаёт число повторных попыток после первой (по умолчанию `2`; `0` — без повторов).

На каждый файл даётся первая попытка и **два повтора**, только для оставшихся неудач. Перед повтором обновляются временные ссылки. После третьей неудачи запись попадает в `corrupted`, сохранённые данные переносятся туда, и обработка курса продолжается. Недоступный файл может не иметь локальных данных: запись всё равно будет в `failed.json`. Ранее сохранённые неудачи остаются в папках с датой; существующие данные не перезаписываются при переносе.

aria2 сохраняет метаданные продолжения каждые 30 секунд. Продолжение требует поддержки HTTP Range сервером; при её отсутствии `--always-resume` приводит к ошибке вместо молчаливого скачивания заново. При жёстком отключении питания сохранность последних записей зависит также от файловой системы. Полностью загруженные файлы проверяются SHA-256 от Яндекса и локальным пересчётом. По умолчанию повторный запуск пропускает обработанные курсы и использует предыдущие подтверждения SHA-256 для готовых файлов незавершённого курса без повторного чтения содержимого. Проверяются размер, наличие `.aria2` и время изменения, если оно было сохранено в подтверждении. Для старых подтверждений без времени изменения используется прежний SHA-256 и размер; скрытые изменения содержимого обнаружит только `--deep`. Новые загрузки всегда проверяются SHA-256.

При временной ошибке получения списка курса даются первая попытка и `--retries` повторов через 60 секунд; внутри API остаётся до пяти сетевых попыток на страницу. Постоянные HTTP-ошибки (например, 404) сразу останавливают запуск с ошибкой API и незавершённым статусом курса. Нехватка места останавливает загрузку. Системные proxy-переменные отключены для API и aria2: нужен прямой доступ к Яндексу. Временные ссылки сохраняются в закрытой папке `.download`; не публикуйте её вместе с кодом.

После исчерпания обычных попыток загрузчик самостоятельно запрашивает пропущенные диапазоны HTTP Range, включая области после недоступной части. Один HTTP 500 не останавливает обработку остальных областей. Начинаем диапазонами до **16 МиБ**. Оставшиеся неудачные области уточняем запросами половинного размера, проверяя обе стороны. При размере кандидата **1 МиБ или меньше**, либо **больше 32 неудачных диапазонов** за проход, переключаемся на линейную проверку блоками **64 КиБ**, не более **256 запросов на файл за запуск**. При `--retries 2` допускается до четырёх уровней детализации; при `--retries 0` после первой пробы сразу выполняется ограниченный линейный проход. Успешные диапазоны повторно не запрашиваются. Его позиция `salvage_cursor` сохраняется в Range-журнале; следующий запуск продолжает поиск дальше. `unprobed` в журнале показывает число ещё не проверенных мелких диапазонов. Этот предел сохраняет время для очереди остальных видео: полностью недоступный гигабайт иначе потребовал бы около 45 минут только мелких запросов. Поиск ограничен размером 64 КиБ и бюджетом, поэтому не гарантирует обнаружение каждого доступного байта.

Это размеры клиентских запросов: подтверждённый актуальный размер физических блоков Яндекс Диска неизвестен. Короткий ответ 206 принимается только как префикс запрошенной области с тем же общим размером файла. Он и префикс, прочитанный до timeout/обрыва, сохраняются; непрочитанный остаток повторяется. При SIGINT новые запросы отменяются, активные заканчивают текущую операцию чтения, их полученные данные записываются перед выходом. Перед каждым проходом ссылка обновляется и проверяются размер и SHA-256 исходного объекта. Одновременно выполняется до 4 Range-запросов, не более 12 новых запросов в секунду. Обычная загрузка через aria2 использует до 2 файлов одновременно и дисковый кеш 256 МиБ.

Подтверждённые новые диапазоны сохраняются рядом с архивным телом в `.ranges.json` после записи данных на диск; исходный `.aria2` сохраняется. Неудача регистрируется до переноса тела и начала Range-восстановления, чтобы остановка не оставила архив вне очереди. Обычный перезапуск незавершённого курса сначала продолжает его зарегистрированные архивные диапазоны, не начиная файл заново через aria2. Повреждённый `.aria2` сохраняется; достоверный независимый `.ranges.json` остаётся пригодным. Перезапуск не запрашивает уже записанные области. Полная восстановленная копия считается готовой только после SHA-256. При полном покрытии с неправильным SHA старое тело сохраняется, частичная доступность для него не подтверждается; выполняется один ограниченный повтор получения в отдельное тело. Если нет достоверного журнала диапазонов, имеющееся тело также сохраняется отдельно.

Для отдельного прохода по **старым** неудачам добавьте `--retry-check` к обычной команде запуска: сначала восстанавливается `corrupted` **только выбранных курсов**, затем продолжается очередь курсов. Завершённые курсы с неудачами вновь обрабатываются; уже готовые оригиналы пропускаются, а их счётчики восстанавливаются из подтверждений при необходимости. Оборванная последняя строка событий удаляется под блокировкой до новой записи; повреждение внутри журнала считается ошибкой.

Проверки замечаний из ревью без сети и настоящих архивов: `python3 -m unittest -q test_regressions test_resume`.

Частичная копия сохраняется рядом с оригиналами с суффиксом ` (partially available)`, если получено **строго больше 50% подтверждённых байтов**. Перед публикацией частичной копии её ожидаемый inode/размер/mtime сохраняются в реестре вместе с предыдущей записью; перезапуск завершает регистрацию или повторяет копирование. Архивное тело и журналы остаются в `corrupted`. Процент считается по подтверждённым диапазонам `.aria2` и `.ranges.json`, а не по размеру файла на диске. Пустые промежутки не засчитываются. Процент байтов не гарантирует воспроизводимость или соответствующую долю времени видео; расчёт времени для частичных копий больше не применяется.

Разово создать такие копии без сетевых запросов:

```bash
python3 download.py recover --destination "$YDS_DEST"
python3 download.py report --destination "$YDS_DEST" --repo ~/gitRepos/ysda-video-backup --mark Walterit
```

В Markdown меняются только ячейки таблиц: `Walterit (partially available; байтов YY.YY%)`. В таблицах и сообщениях показывается только процент подтверждённых байтов; порог сохранения также определяется по байтам. Такая отметка не подтверждает полный оригинал и не делает курс полностью скачанным. Когда оригинал полностью восстановлен и проверен SHA-256, собственная частичная отметка заменяется полной в той же ячейке. Существующая отметка полного оригинала и чужие отметки сохраняются. Изменённые вручную частичные копии загрузчик не перезаписывает.

В журнале ищите `RANGE PASS`, `PARTIALLY AVAILABLE` и `RECOVERY ERROR`. Текущие данные `corrupted` можно свести командой `python3 download.py corrupted --destination "$YDS_DEST"`: она обновляет `corrupted/progress.json` и `corrupted/Прогресс загрузки.txt`.

Код завершения: `0` — все выбранные курсы проверены; `1` — обработка закончилась с недоступными/повреждёнными файлами; `2` — ошибка настройки, API при получении каталога или среды.

## Отметить копии в ysda-video-backup

Результаты можно перенести в существующие карточки форка:

```bash
python3 download.py report --destination "$YDS_DEST" \
  --repo ~/gitRepos/ysda-video-backup --mark Walterit
```

`--mark` — произвольный ник/отметка владельца копии. Подтверждённые SHA-256 файлы получают этот ник в первой свободной колонке «Копия 1–3»; чужие отметки сохраняются. При заполнении всех колонок команда останавливается с ошибкой. Неудачи после исчерпания попыток перечисляются отдельно; промежуточные ошибки считаются ожидающими повтора. Отчёт использует последние записи журнала и проверяет наличие/размер локальных файлов, без повторного чтения всех видео для вычисления хеша. Карточки сопоставляются по источнику и полному пути, с учётом Unicode; имя файла карточки и год не зашиты в код.

Для автоматического обновления после каждого курса добавьте к обычному запуску:

```bash
./start.sh "$YDS_DEST" --catalog "$PWD/catalog.json" \
  --report-repo "$HOME/gitRepos/ysda-video-backup" --mark Walterit
```

Команда меняет рабочие файлы локального форка. Без `--git-push` commit/push выполняются вручную; пересборка всего каталога не запускается. Отчёт ограничен курсами, для которых есть записи проверок. Если данные разных лет хранятся в разных папках, выполните `report` для каждой папки. Маркировка `копия есть` требует подтверждения всех файлов таблицы; частичные результаты не выдаются за полную копию. Подробные отчёты хранятся только локально в `.download/catalog-reports/ИМЯ-КАРТОЧКИ.md`. В форке обновляются только отметки владельцев копий, статусы курсов и сводка README; менять генератор каталога не требуется.


### Автоматический commit/push после курса

```bash
./start.sh "$YDS_DEST" --catalog "$PWD/catalog.json" \
  --report-repo "$HOME/gitRepos/ysda-video-backup" --mark Walterit --git-push
```

После каждого обработанного курса, включая курсы с неудачами, загрузчик сохраняет подробный отчёт локально, обновляет отметки в форке, создаёт коммит и выполняет `git push origin HEAD`. Сообщение коммита содержит отметку владельца, название архива (год/семестр) и курс. В коммит попадают только изменённые карточки курсов и сводка README. Если изменений нет, пустой коммит не создаётся, но push выполняется: это повторная попытка отправить ранее оставшийся локальный коммит.

В форке должны быть настроены `origin`, Git author и доступ SSH к GitHub. Индекс должен быть пустым; существующие правки в обновляемых карточках или README блокируют публикацию. Правки других файлов сохраняются и не добавляются в коммит. Успешный push отмечается `REPORT PUSHED` в журнале. Автоматическая публикация работает в фоне. Задание сохраняется до отметки курса завершённым; ошибка отчёта, commit или push отмечается `REPORT PENDING`. Повтор выполняется после восстановления локальной сети либо с задержкой 30–300 секунд при другой ошибке; после перезапуска сохранённые задания продолжаются без повторного скачивания курса. При отказе push локальный коммит сохраняется. Git-публикация использует IPv4 по умолчанию; заданный `GIT_SSH_COMMAND` сохраняется. Перед изменением MD создаётся локальный журнал `.git/yds-report-transaction.json`: после обрыва commit восстанавливаются только собственные правки, а новые пользовательские изменения блокируют автоматический повтор. Force push, pull и автоматическое разрешение конфликтов не выполняются.

Разовую публикацию можно выполнить так:

```bash
python3 download.py report --destination "$YDS_DEST" \
  --repo ~/gitRepos/ysda-video-backup --mark Walterit --git-push
```


### Уже скачанные видео в других локальных папках

Отчёт также учитывает `.download/local-copies.json`: реестр локальных копий, для которых SHA-256 сверили с Яндексом. Запись содержит источник `source`, полный путь видео в источнике `path`, локальный путь `local`, размер `size`, `sha256`, `mtime_ns`, время проверки `time`, статус `valid`, курс `course`, номер попытки `attempt` и пояснение `detail`. Локальные пути остаются в папке загрузки, в Git публикуются только отметки копий.

Подтверждённая внешняя копия учитывается даже если скачать этот файл в текущую папку не удалось. При исчезновении файла, изменении размера/времени модификации или наличии `.aria2` отметка перестаёт считаться подтверждённой. Реестр не переносит видео и не заменяет резервное копирование на другой диск. Для регистрации нового файла сначала нужно проверить его SHA-256, совпадения одного имени/размера недостаточно.

### Память Range-worker

При большом числе потоков glibc может удерживать свободные буферы в отдельных аренах. На Linux с glibc запускайте worker с `MALLOC_ARENA_MAX=2`, например `MALLOC_ARENA_MAX=2 python3 range_queue.py ...`; для `systemd-run` добавьте `--setenv=MALLOC_ARENA_MAX=2`. Настройка читается при старте процесса, поэтому потребуется перезапуск. Она ограничивает число арен, а не память активных запросов; RAM по-прежнему зависит от параллельности и размера блока.

## Очередь архивов по годам и семестрам

`semester_queue.py` запускает архивы последовательно, а загрузчик внутри каждого архива — курсы по порядку JSON. Каталог допускает вложенные пути курсов, например `Весна 2021/Компьютерные сети`. У каждого архива своя папка `.download`, журналы, проверки SHA-256 и `corrupted`. AI/ML можно отключить через `enabled: false` в каталогах; по умолчанию загрузчик выбирает все курсы.

Пример `queue.json` (пути должны быть абсолютными):

```json
{
  "retries": 2,
  "retry_check": false,
  "archives": [
    {
      "title": "2025 осень",
      "catalog": "/absolute/path/2025-autumn.json",
      "destination": "/absolute/path/YandexDisk/ШАД осень 2025",
      "enabled": true,
      "state": "pending"
    }
  ]
}
```

Для автоматической публикации добавьте в корень JSON `report_repo`, `mark` и `git_push: true`. Чтобы дождаться текущего одиночного запуска, добавьте `wait_for: {"unit": "yds-download.service", "destination": "/absolute/path/current-archive"}`: очередь проверит, что каждый выбранный курс действительно обработан, прежде чем перейти дальше.

```bash
python3 semester_queue.py /absolute/path/queue.json
```

Для фонового запуска используйте отдельный юнит:

```bash
systemd-run --user --unit=yds-download-queue --collect   --property=KillSignal=SIGINT --property=SuccessExitStatus=130 --property=TimeoutStopSec=90   --property=StandardOutput=append:/absolute/path/queue.log   --property=StandardError=append:/absolute/path/queue.log   python3 "$PWD/semester_queue.py" /absolute/path/queue.json
```

Наблюдение: `tail -f /absolute/path/queue.log`, `cat /absolute/path/queue.json`. `finished` означает завершение обработки, включая файлы, исчерпавшие попытки; полноту копии смотрите в `.download/summary.json` и статусах курсов. Код загрузчика `1` сохраняется как `exit_code`, очередь продолжает следующий архив; ошибка настройки или нехватка места останавливает очередь с `blocked`. При повторном запуске обработанные архивы пропускаются. Перед редактированием работающей очереди остановите её: `systemctl --user stop yds-download-queue.service`; частичные загрузки сохранятся.

OBS с отметкой «полнота не проверена» не считается подтверждением полной копии файла или курса.

### Продолжение и отдельная глубокая проверка

Завершение курса сохраняется в `.download/course-history.json` по имени курса и источнику, независимо от номера в выборке. Обычный перезапуск сохраняет отметки и продолжает с незавершённого курса. История прежних запусков автоматически импортируется из `NN-status.json`; `finished` с неудачами означает, что попытки исчерпаны, а не что все видео доступны. Коды завершения и сводка сохраняют такие неудачи даже при пропуске курса.

Отдельная проверка SHA-256 выбранного курса без скачивания:

```bash
./start.sh "$YDS_DEST" --catalog "$PWD/catalog.json" \
  --include "Название курса" --deep
```

`--deep` проверяет SHA-256 локальных оригиналов, включая найденные внешние копии, и записывает отсутствующие/повреждённые файлы без скачивания. `--retry-check` повторяет загрузку и Range-восстановление предыдущих неудач, используя кеш SHA-256 готовых оригиналов. Флаги можно сочетать для проверки и исправления. В JSON очереди используются независимые `deep` и `retry_check`; по умолчанию оба `false`.

Обычный перезапуск продолжает прерванное восстановление, но пропускает завершённые попытки даже внутри незавершённого курса. Состояние каждого файла атомарно сохраняется в `.download/recovery-state/XX/HASH.json`: `running` перед попыткой, `finished` после результата. Изменение SHA-256/размера отменяет прежнее подтверждение; `--retry-check` явно разрешает новый проход. Старые флаги удалены.

### Состояние отдельных файлов

Передача и восстановление используют отдельные записи в
`.download/transfer-state/XX/HASH.json` и `.download/recovery-state/XX/HASH.json`.
`HASH` — SHA-256 исходного пути файла, `XX` — первые два символа хеша.
Запись содержит исходный путь и состояние; при чтении принадлежность проверяется.
Обновление читает и записывает только нужную запись, без обхода остальных файлов.
Атомарная замена и `fsync` сохраняются; межпроцессная блокировка защищает запись и миграцию.
Задачи `.download/tasks/`, журналы, данные видео и SHA/Range-доказательства не меняются.

При первом обращении старые `transfer-state.json` и `recovery-state.json`
автоматически разделяются на записи. Миграция после прерывания продолжается,
уже созданные записи не перезаписываются. Только после сохранения всех записей
старый JSON переименовывается в `*.json.migrated` и остаётся резервной копией.
Миграция один раз читает старый JSON целиком и может занять время на HDD.

Перед первым запуском новой версии остановите **все** загрузчики и Range-worker,
использующие эти архивы. После миграции запускайте только новую версию:
старый код не читает отдельные записи, а резервный JSON после новых обновлений устаревает.
Автоматического отката формата нет. Всё состояние остаётся приватным внутри `.download`.

### Сколько успело скачаться до ошибки

Каждая новая запись в `events.jsonl` и `corrupted/**/failed.json` содержит `downloaded_bytes`, `downloaded_percent`, `progress_source` и `local_size`. Процент для частичной загрузки берётся из битовых карт `.aria2`, включая сохранённые блоки незавершённых частей. Размер MP4 может включать незаполненные промежутки, поэтому не используется как число скачанных байтов. Это объём сохранённых блоков, а не подтверждение SHA-256 или воспроизводимости видео. При неизвестном формате метаданных процент остаётся `null`, ошибка сохраняется как `progress_error`. Без файла — 0%; успешная проверка SHA-256 — 100%.

Восстановить сведения для прежних неудач, сохранить общий JSON/TXT и вывести оставшиеся файлы с долей **больше 30%**:

```bash
python3 download.py corrupted --destination "$YDS_DEST"
```

Результаты остаются локально в `corrupted/progress.json` и `corrupted/Прогресс загрузки.txt`. Процент, записанный при неудаче, сохраняется даже при последующем переносе тела; `retained` показывает его наличие сейчас. Отсутствие `.aria2` у существующего повреждённого файла означает неизвестную долю, а не 100%.


## Настройка скачивания и Range

Описание адаптивного поиска и результаты проверки: [Range benchmark](docs/range-search-benchmark.md).

Перед Range-восстановлением запрашиваются метаданные только нужного файла, без обхода папки. Размер и SHA-256 сверяются с сохранёнными; ссылка используется во всех проходах и обновляется при HTTP 401/403 с повторной проверкой идентичности. Уже полностью сохранённые диапазоны не требуют сетевого запроса: целостность проверяется локальным SHA-256.

Все значения по умолчанию сохраняют прежние настройки. Список флагов и дефолтов:

```sh
python3 download.py download --help
```

Пример более осторожного режима записи на диск:

```sh
./start.sh /absolute/path/YandexDisk --catalog /absolute/path/catalog.json \
  --download-concurrency 1 --connections 2 --split 2 \
  --disk-cache-mib 128 --range-workers 2 --range-rps 8
```

Для HDD, если важнее минимизировать перемещения головок, чем скорость, можно начать
с `--download-concurrency 1 --connections 1 --split 1 --range-workers 1`.
Это ограничивает одновременные записи; проверка SHA-256 и восстановление Range
могут дополнительно нагружать диск. Универсальной гарантии последовательной записи
нет — проверяйте фактическую нагрузку. Для SSD параллелизм обычно можно увеличить.

Настройки текущего запуска сохраняются в `.download/settings.json`. Они описывают последний запуск; новый запуск берёт дефолты и переданные флаги, автоматически сохранённые настройки не подхватывает.

| Флаг | По умолчанию | Назначение |
|---|---:|---|
| `--download-concurrency` | `2` | Simultaneous files |
| `--connections` | `4` | Connections per server per file |
| `--split` | `4` | Download splits per file |
| `--min-split-size-mib` | `4` | Minimum aria2 split size, MiB |
| `--disk-cache-mib` | `256` | aria2 disk cache, MiB; 0 disables |
| `--bandwidth-limit` | `0` | Total aria2 limit, bytes/second; 0 unlimited |
| `--auto-save-interval` | `30` | Resume metadata save interval, seconds |
| `--connect-timeout` | `20` | aria2 connection timeout, seconds |
| `--timeout` | `60` | aria2 timeout, seconds |
| `--summary-interval` | `30` | aria2 progress interval, seconds |
| `--retry-delay` | `10` | Delay between download retries, seconds |
| `--listing-retry-delay` | `60` | Delay between course-listing retries, seconds |
| `--free-space-mib` | `1024` | Free space to retain in addition to required bytes, MiB |
| `--range-workers` | `2` | Simultaneous Range requests |
| `--range-rps` | `12` | Range requests/second per recovery |
| `--range-timeout` | `30` | Range request timeout, seconds |
| `--range-retry-delay` | `10` | Delay between Range passes, seconds |
| `--range-block-size-kib` | `16384` | Initial Range block, KiB |
| `--range-min-block-size-kib` | `1024` | Switch to linear probing at this block size, KiB |
| `--range-linear-block-size-kib` | `64` | Linear probe block size, KiB |
| `--range-failure-limit` | `32` | Switch to linear after more failed ranges than this |
| `--range-linear-probes` | `256` | Maximum scatter/expansion/linear requests per recovery |
| `--range-max-passes` | `0` | Maximum Range passes; 0 = min(4, 2*retries)+2 |

MiB = 1 048 576 байт; KiB = 1024 байта. `--bandwidth-limit` ограничивает суммарную скорость aria2, в байтах/с; на независимые Range-запросы он не распространяется. Их параллельность и частоту задают `--range-workers` и `--range-rps`. `--range-max-passes 0` сохраняет прежнюю формулу по `--retries`; положительное значение задаёт верхний предел. Если крупный проход не дал ни байта, после превышения `--range-failure-limit` оставшиеся крупные запросы откладываются и следующий проход начинает мелкие пробы по всему пропуску. После перехода к мелким пробам до половины бюджета `--range-linear-probes` распределяется по всему оставшемуся пропуску. До четверти бюджета используется для более крупных запросов по обе стороны найденных данных; уже неудачные запросы уменьшаются, а одинаковые мелкие пробы не повторяются в этом проходе. Остаток бюджета отведён линейному поиску, его отдельный курсор сохраняется для следующего явного `--retry-check`. Разреженные пробы не доказывают отсутствие данных между ними: журнал содержит только действительно полученные байты, а `unprobed` показывает оставшиеся непроверенные мелкие диапазоны. Настоящий размер блоков хранилища Яндекса неизвестен; алгоритм не предполагает единственную границу доступности.

Размеры Range должны удовлетворять `linear <= minimum <= initial`. Передаваемые параметры проверяются до запуска скачивания. Проверки SHA-256, сохранение доказанных диапазонов и порог **строго больше 50% байт** для частичных копий сохраняются.

В JSON очереди параметры находятся в `tuning`; ключи соответствуют флагам с подчёркиваниями. Общие значения можно переопределить для конкретного архива:

```json
{
  "tuning": {"download_concurrency": 2, "range_workers": 4},
  "archives": [
    {
      "title": "2025 осень",
      "catalog": "/absolute/path/2025-autumn.json",
      "destination": "/absolute/path/YandexDisk/ШАД осень 2025",
      "tuning": {"download_concurrency": 1, "range_workers": 2}
    }
  ]
}
```

Изменение настроек требует перезапуска процесса. Для одного файла завершённое восстановление по-прежнему не повторяется без `--retry-check`, даже при новых параметрах Range.


### Защита сохранённых диапазонов и смена исходного файла

При первом независимом Range-проходе имеющиеся доказательства `.aria2` импортируются в нормализованный `.ranges.json` с отметкой `control_imported: true`. После этого журнал служит единственным источником диапазонов: рост файла не возвращает старые доказательства за прежней границей тела. Исходный `.aria2` сохраняется в архиве.

`.download/resume-identities.json` связывает файл продолжения с SHA-256 и размером исходника. Если они изменились или принадлежность существующего `.aria2` нельзя подтвердить, обычный запуск сохраняет прежнее тело и метаданные в `corrupted/*-source-change/` и начинает новый файл. `source-change.json` описывает старую и новую идентичность; такие архивы не выдаются за неудачи текущего исходника. `--deep` сохраняет исходные файлы и только проверяет их. При создании нового тела восстановления его путь сразу записывается в состояние, чтобы следующий запуск продолжал именно его.

Глубокая проверка рассматривает основную и зарегистрированные внешние копии независимо. Исчезнувшая внешняя копия не скрывает целый основной файл. При `--deep --retry-check` уже восстановленный оригинал подтверждается SHA-256 до попыток Range.


### Автоматический подбор параллельности

Для подбора по скорости реальных файлов можно включить штатную эвристику aria2:

```sh
./start.sh /absolute/path/YandexDisk --catalog /absolute/path/catalog.json \
  --auto-concurrency --download-concurrency 4
```

`--download-concurrency` задаёт верхний предел одновременно обрабатываемых файлов. В режиме `--auto-concurrency` aria2 выбирает их число по наблюдаемой скорости и формуле `N = A + B * log10(скорость в Мбит/с)`. Дефолты коэффициентов: `--auto-concurrency-a 1`, `--auto-concurrency-b 2`. Это эвристика aria2, а не поиск максимума по заданной скорости тарифа; достижение всей полосы не гарантировано. Проверка SHA выполняется отдельно от слотов передачи. Range-восстановление использует отдельные настройки и не меняется этим флагом.

Без флага сохраняется фиксированная параллельность, по умолчанию 2. `--no-auto-concurrency` явно отключает автоматический режим. В очереди: `"tuning": {"auto_concurrency": true, "download_concurrency": 4}`. Скорость 82–93 Мбит/с соответствует примерно 9,8–11,1 МиБ/с.

Документация: https://aria2.github.io/manual/en/html/aria2c.html#cmdoption-optimize-concurrent-downloads

### Подбор скачивания по измеренному приросту скорости

`--download-budget "$HOME/.local/state/yds-download/download-budget"`
включает наш подбор по реальным новым байтам, вместо формулы aria2 выше.
`--download-min-files 2 --download-max-files 8` задают **общий** диапазон
для Яндекса, Nextcloud и OpenCloud, включая фоновые загрузки из резервных облаков.
Для совместной работы передавайте одинаковые три параметра в `semester_queue.py`
и `range_queue.py`; у `download.py download` они также доступны.
Этот бюджет независим от `--upload-budget` и ограничения Range-запросов.

Контроллер пробует добавить один файл, сравнивает 90-секундные окна скорости
и откатывает пробу без достаточного прироста. При нулевой скорости допускается
ограниченная проба: отсутствие новых байтов приводит к откату и паузе перед
следующей пробой. Начатые файлы при уменьшении лимита не прерываются.
Яндекс качает через прежний aria2, но каждая задача допускается через общий
бюджет посредством локального RPC с временным токеном. Повтор сетевого запроса
сохраняет `.aria2` и не учитывает старые байты второй раз.

Текущие слоты, ожидающие файлы и суммарная скорость — в
`download-budget/state.json` (`controller.limit`, `controller.last_rate` в байт/с,
`controller.last_rate_time`, участники `yandex`, `nextcloud`, `opencloud`).
Файл мал и перезаписывается; payload и состояния возобновления остаются на HDD.

Для резервного OpenCloud добавьте к тем же командам:
`--opencloud-fallback https://ysda-recover-dsk.jumpingcrab.com --opencloud-username Walterit --opencloud-password-file "$HOME/.jumpingcrub.apptoken"`.
Nextcloud подключается прежним `--nextcloud-fallback URL`.
Резервные копии рассматриваются после обычных попыток Яндекса и только для
видео ШАД, указанных в его manifest. Начатая резервная копия имеет приоритет;
затем проверяются Nextcloud и OpenCloud. Один снимок метаданных OpenCloud
переиспользуется между архивами; payload для поиска не скачивается.
Подходящий известный хэш позволяет сопоставить переименованный файл; иначе
нужны название, размер, курс и семестр. Оригиналом считается только локальная
копия, прошедшая SHA-256 из Яндекса. Альтернатива с другим SHA сохраняется отдельно
с суффиксом источника. Без общего доступного хэша невозможно заранее доказать,
что две резервные копии побайтно одинаковы; такую копию требуется прочесть.

### Личные файлы по публичной ссылке

Для опубликованной папки целиком (включая файлы в корне и подпапки) или одного файла:

```sh
mkdir -p /absolute/path/backup/folder
./start.sh /absolute/path/backup/folder --source PUBLIC_URL --root
```

Для каждой ссылки используйте отдельную папку назначения: состояние привязано к источнику. OAuth не нужен. Сохраняются прежние SHA-256 проверки, продолжение и Range-восстановление. Логи и метаданные находятся в `.download/`; личные файлы и состояние не отправляются в Git. Режим `--root` несовместим с публикацией отчётов о курсах. Каталог для этого режима создаётся командой `python3 download.py catalog --source PUBLIC_URL --root --output catalog.json`.

### Длинные имена файлов

Локальные компоненты пути длиннее 230 байт UTF-8 сокращаются: читаемое начало, `~` и 16 шестнадцатеричных символов SHA-256 исходного имени, затем расширение. Зарезервировано место для `.aria2`, журналов Range и `(partially available)`. Исходные пути в манифестах, логах и таблицах остаются полными; то же преобразование используется для загрузки, проверок, архивирования и восстановления. Если два исходных пути дают одинаковый локальный путь, загрузка останавливается до записи файлов.

Ранее сохранённые файлы с именами от 231 до 255 байт автоматически не переименовываются; перед обновлением такой архив следует отдельно перенести на новую схему, сохранив его доказательства SHA.

### Общая очередь восстановления Range

Обычные загрузчики запускаются с `semester_queue.py QUEUE.json --defer-range`:
после SHA и обычных повторов они сохраняют задачи Range и переходят к следующему
архиву. Курс остаётся `recovering`; завершённым он становится после обработки
всех задач. Перезапуск не повторяет уже завершённые обычные загрузки.

Отдельный общий процесс обслуживает обе очереди в порядке приоритета:

```sh
python3 range_queue.py --queue PERSONAL_QUEUE.json --queue SEMESTER_QUEUE.json
```

По умолчанию: `--files 4 --requests-per-file 2 --requests 12 --rps 12`.
Ограничения запросов общие для обеих очередей; при наличии работы для курсов
им оставляется один слот. `--secondary-slots N` задаёт число слотов для
последующих очередей, когда первая тоже занята; например, `--files 8
--secondary-slots 4` даёт личным файлам и курсам по четыре слота. Если одна
очередь свободна, другая использует все слоты. Действуют сохранённые таймауты и размеры блоков
каждого архива. Архивы, которые ещё пишет обычный загрузчик, защищены блокировкой.
При остановке сохраняются подтверждённые блоки; при следующем запуске worker
продолжает незавершённые задачи. Без `--defer-range` остаётся обычный режим
восстановления внутри загрузчика.

В текущем развёртывании общий лог — `YandexDisk/.download/range-queue.log`,
сервис — `yds-download-range.service`. Проверка:

```sh
systemctl --user status yds-download-range.service
journalctl --user -u yds-download-range.service -n 30
# Для файловых логов: tail -f /absolute/path/YandexDisk/.download/range-queue.log
```

При запуске через `services.py` постоянные лимиты Range уже заданы в
`services.range.properties` единого JSON-конфига. Старые установленные drop-in
с лимитами и окружением уберите, сохранив нужные значения в JSON: иначе systemd
может продолжать применять их поверх настроек запуска.

Для ручного запуска без `services.py` можно использовать поставляемый systemd
drop-in (размеры указаны в двоичных единицах: 2560 MiB = 2,5 GiB):

```sh
install -Dm0644 deploy/systemd/user/yds-download-range.service.d/10-memory.conf \
  "${XDG_CONFIG_HOME:-$HOME/.config}/systemd/user/yds-download-range.service.d/10-memory.conf"
systemctl --user daemon-reload
systemctl --user restart yds-download-range.service
systemctl --user show yds-download-range.service \
  -p MemoryHigh -p MemoryMax -p EffectiveMemoryHigh -p EffectiveMemoryMax -p MemoryCurrent
```

`MemoryHigh=2560M` начинает ограничивать потребление на уровне cgroup, включая
файловый кэш; `MemoryMax=3072M` задаёт жёсткий предел, при котором возможен
OOM-kill. Файл в репозитории **не меняет настройки работающего сервера** до
установки drop-in, `daemon-reload` и перезапуска unit. При меньших лимитах
родительского slice проверьте `EffectiveMemoryHigh` и `EffectiveMemoryMax`.

Перед ручной проверкой `--deep`/`--retry-check` или изменением Git-репозитория
отчётов остановите обычный загрузчик курсов и общий worker, чтобы освободить
блокировки архива и публикации. `.download` и личные данные в Git не попадают.

### Повторная проверка доступности Яндекса

```sh
python3 range_queue.py --queue PERSONAL_QUEUE.json --queue SEMESTER_QUEUE.json \
  --files 16 --secondary-slots 8 --recheck-interval 86400 --recheck-files 8 \
  --requests 12 --rps 5 --budget /data/.download/http-budget
```

`--recheck-interval` по умолчанию равен `0`: завершённые попытки не повторяются.
При включении незавершённые оригиналы и частичные копии снова проверяются через
Яндекс; подтверждённые блоки используются повторно. SHA-подтверждённые полные
копии, а также задачи, уже заменённые актуальными манифестами или подтверждёнными
копиями (локальными либо Nextcloud), пропускаются. Для повторной проверки
исчезнувшей удалённой копии перезапустите обычную загрузку с обновлённым
`--nextcloud-existing` или без него. Для тела, уже отвергнутого по SHA, создаётся новая копия:
старые байты сохраняются отдельно и не используются как доказанные.
Первый проход включает старые ошибки без даты проверки.
Следующая попытка файла начинается не раньше чем через указанный интервал после
завершения предыдущей; дата `yandex_checked_at` хранится в задаче и переживает
перезапуск. Если весь проход занимает больше суток, параллельный дубликат не
запускается. Прерывание оставляет задачу для продолжения.

`--recheck-files 8` добавляет восемь слотов к обычным шестнадцати: четыре для
первой очереди (личные файлы), четыре для остальных (курсы). Архивы чередуются;
существующие сетевые ограничения остаются общими. Перепроверки конкурируют за
диск и сеть, но не занимают обычные файловые слоты. Основной загрузчик продолжает
работать, активный архив защищён его блокировкой. Указанный в `wait_for` старый
архив, например весна 2026, включается в перепроверку по сохранённым манифестам
ошибок без повторного запуска загрузчика семестров. Успешные результаты обновляют
обычные журналы, статус курса и Markdown тем же способом, что остальные Range-задачи.

В общем логе ищите `YANDEX RECHECK START` и `YANDEX RECHECK FINISHED`.
В метриках есть `range_recheck_active_files`, `range_recheck_eligible_files` и
`range_regular_active_files`; `range_active_files` включает оба вида задач.
Счётчики архива: `yandex_rechecks` и `yandex_recheck_full_files`.

Recheck начинает с ограниченной проверки доступности: `--recheck-probes 16`
задаёт до 16 диапазонов на файл. Первый запрос имеет обычный размер Range-блока
(по умолчанию до 16 MiB), остальные распределены по пропущенным байтам и имеют
размер линейного блока (обычно 64 KiB). После первого полученного блока запускается
обычное адаптивное восстановление; проверка SHA-256 полных файлов сохраняется.
Если данных нет, попытка завершается до следующего Recheck, позиции проб меняются.
Сетевые ретраи внутри запроса сохраняют прежние правила и не входят в этот лимит.

`--recheck-full-interval 604800` заставляет делать полный проход раз в неделю,
даже если малые пробы ничего не нашли. Дата `yandex_full_recheck_at` хранится
в задаче, положительная проба сохраняет решение продолжить восстановление до
записи байтов. При перезапуске такой файл продолжает полный проход. Для старых
задач недельный интервал считается от последней завершённой проверки; для
файлов без истории — от первой новой попытки. `--recheck-probes 0` или
`--recheck-full-interval 0` отключает быстрый режим. Обычные Range-задачи
обрабатываются прежним алгоритмом.

В логе `RANGE PROBE` показывает число запросов, новые байты и переход к полному
проходу. В `range_attempts` быстрая фаза записана как `attempt: 0`, запросы имеют
`mode: "probe"`. Счётчики архива: `recheck_probe_runs`, `recheck_probe_requests`,
`recheck_probe_positive`, `recheck_probe_empty`, `recheck_probe_new_bytes`,
`recheck_probe_seconds` и `recheck_full_attempts`. Отрицательные пробы не доказывают,
что других доступных блоков нет: их может обнаружить следующий либо недельный проход.


Сводки `corrupted/**/failed.json` содержат метаданные, прогресс и отметку
`range_attempted`, без списков каждого HTTP-запроса. Подробности `range_attempts`
сохраняются в состоянии каждого файла (`recovery-state/`), задачах и журнале событий.
Range-планировщик хранит границы пропусков и вычисляет нужные блоки по индексу;
количество объектов в плане зависит от числа пропусков, а не от размера файла.

### Измерения Range

В `range_attempts` сохранены длительности каждого запроса: `seconds` включает
ожидание лимитера, `request_seconds` — сеть, `first_byte_seconds` — время до
первых данных (null при пустом ответе), `save_seconds` — запись блока и
подтверждений. У прохода есть общее `seconds`. Строки `RANGE PASS` в общем
логе содержат время, сумму сетевого времени, время сохранения, новые байты
и p95 времени до первых данных среди непустых ответов этого прохода. Сетевое
время суммируется по параллельным запросам и может превышать время прохода.
Эти измерения появляются у новых запросов; у прежних записей полей нет.

### Range одновременно с обычным скачиванием

Передайте всем трём процессам один каталог бюджета:

```sh
python3 semester_queue.py PERSONAL_QUEUE.json --defer-range --range-budget /data/.download/http-budget --range-files 16
python3 semester_queue.py SEMESTER_QUEUE.json --defer-range --range-budget /data/.download/http-budget --range-files 16
python3 range_queue.py --queue PERSONAL_QUEUE.json --queue SEMESTER_QUEUE.json --files 16 --secondary-slots 8 --budget /data/.download/http-budget
```

Загрузчик выполняет Range в отдельном пуле параллельно aria2 и SHA,
сохраняя исключительное владение состоянием своего архива. После завершения
обычных загрузок, SHA и повторных попыток он останавливает оставшиеся Range,
сохраняет блоки и передаёт незавершённые задачи worker'у без ожидания их окончания.
Бюджет ограничивает суммарно все процессы восемью Range HTTP-запросами и
12 стартами запросов в секунду. Лимиты worker'а `--requests` / `--rps` должны
совпадать с бюджетом загрузчиков (8 / 12); несовпадение отвергается.
`--range-files` ограничивает файлы каждого загрузчика; `--range-workers` —
запросы одного файла. Без `--range-budget` прежний отложенный режим сохраняется.

Для личных папок с множеством таймаутов используйте фиксированные
`download_concurrency: 8`, `auto_concurrency: false`, `range_retry_delay: 3`
в `tuning` очереди. Поднимайте параллельность до 16 после измерения темпа
обработки и нагрузки диска; действующие таймауты и проверки SHA сохраняются.

### Статистика сервисов

Сбор включён автоматически; `--metrics-interval` / `tuning.metrics_interval`
задаёт период (по умолчанию 60 секунд). История хранится в JSONL, последний
срез — в соседнем JSON:

| Процесс | История | Последний срез |
|---|---|---|
| Загрузчик / Range своего архива | `DEST/.download/metrics.jsonl` | `DEST/.download/metrics-latest.json` |
| Очередь семестров / личных папок | `QUEUE.metrics.jsonl` | `QUEUE.metrics-latest.json` |
| Общий Range-worker | `FIRST_QUEUE.range.metrics.jsonl` | `FIRST_QUEUE.range.metrics-latest.json` |

Здесь `QUEUE` — путь JSON очереди без расширения `.json`. Каждый срез содержит
`run_id`, PID, роль, версию Git, настройки, накопительные `counters`, изменения
за окно `interval_counters` и длительность окна `seconds`. После перезапуска
счётчики нового `run_id` начинаются с нуля; история остаётся. Срезы `shutdown`
и `handoff` могут иметь короткие окна. Не суммируйте накопительные счётчики
каждой строки: используйте изменения за окно или последний срез каждого запуска.

- `aria_received_bytes`: новые байты по bitmap возобновления и завершённым
  передачам, без уже имевшихся байтов при старте попытки. Повторная передача
  после неудачной проверки SHA учитывается как новая передача. Это объём
  полученных данных, не гарантия исправности. Разрешение прогресса зависит
  от `--auto-save-interval` aria2. Если старый файл не имеет доказательства
  возобновления, первый наблюдаемый объём попадает в
  `aria_initial_unmeasured_bytes`, а не считается новым трафиком.
- `aria_completed_files` / `aria_completed_bytes`: завершённые передачи;
  байты здесь включают сохранённый префикс возобновляемого файла. Проверка
  SHA выполняется отдельно, поэтому эти числа могут опережать `summary.json`.
- `sha_checks`, `sha_seconds`, `sha_verified_bytes`, `sha_valid_files` и
  остальные `sha_*_files`: выполненные проверки и их результат. Восстановленные
  Range оригиналы проверяются внутри восстановления и отражаются в `range_full_files`.
- `range_received_bytes`, `range_requests`, `range_request_seconds`,
  `range_wait_seconds`, `range_io_seconds`, `range_zero_byte_passes`:
  сохранённые блоки и цена поиска, с обновлением после каждого логического
  Range-запроса (он может включать несколько HTTP-попыток).
  Сумма времени параллельных запросов может превышать длительность окна.
- `errors.range` / `errors.aria_error_messages`: накопительные классы ошибок.
  Для aria2 это сообщения журнала, их число не равно числу потерянных файлов;
  `aria_aborted_files` считает сообщения об отменённых передачах.
- `aria_attempt_details`: наблюдения соединений aria2 по CUID, пути файла,
  HTTP-статусу и итоговому коду ошибки. `connect_ready_seconds` измеряет время
  от начала подключения до отправки запроса (TCP + TLS, без DNS),
  `response_headers_seconds` — от отправки запроса до полных HTTP-заголовков
  ответа, `body_phase_seconds` — от заголовков успешного ответа до конца
  наблюдения (ошибка, смена запроса или завершение файла).
  Это длительность всего этапа наблюдения, не время простоя
  и не точный момент первого байта тела. Маркеры берутся из INFO-журнала
  [aria2 1.37.0](https://github.com/aria2/aria2/blob/release-1.37.0/src/HttpConnection.cc).
  Новых запросов и чтения видео для этих замеров нет.
  `request_seconds` учитывает и повторное использование соединения, когда
  отдельное время подключения неизвестно. `started_at` / `ended_at` — Unix-секунды
  из локальных временных меток журнала; неизвестные длительности имеют `null`.
  Одна запись относится к запросу соединения, файл может иметь несколько.
  Завершение сегмента не завершает наблюдение: aria2 может продолжить тот же
  HTTP-ответ для следующего сегмента. `segments_completed` и
  `seconds_since_last_segment` показывают число законченных сегментов и время
  с последнего такого события; это прогресс aria2, а не отметка последнего TCP-пакета.
  При неоднозначном сопоставлении файлов `path` остаётся `null`.
- `aria_timeout_connections` и `errors.aria_timeout_phases`: таймауты отдельно
  на этапах `connect` (TCP/TLS), `response_headers`, `body` или `unknown`.
  `phase`, `stage_seconds`, `outcome` и `censored` в деталях различают
  завершение файла и прерванное наблюдение. `censored=false` означает известное
  успешное завершение файла; это не гарантия полного ответа каждого его соединения.
  Непустые времена подключения и заголовков относятся к уже завершённым этапам
  независимо от итогового исхода файла. Таймаут — нижняя граница
  необходимого ожидания: он не доказывает, что файл недоступен. При остановке,
  потере журнала или вытеснении контекста фиксируется последнее наблюдаемое
  время, без придуманной длительности. `body_phase_seconds` при таймауте
  нельзя использовать как измерение паузы между пакетами.
  Настроенные лимиты находятся в `settings.tuning.connect_timeout` / `timeout`.
- Суммы `aria_connect_ready_seconds`, `aria_response_headers_seconds`,
  `aria_body_phase_seconds` и соответствующие `*_samples` обновляются после
  завершения наблюдений. Успехи и прерывания анализируйте отдельно по деталям.
  Детали используют буфер памяти на 1024 записи и минутную запись метрик;
  `aria_attempt_buffer_overwrites` считает вытеснения, общие счётчики сохраняются.
  Для устранения повторных строк после ошибки записи используйте `run_id` +
  `sequence` внутри `aria_attempt_details`. INFO-журнал находится на диске
  назначения; консоль остаётся WARN. При разборе ошибок промежуточные INFO-цепочки
  исключаются из решений о сетевых повторах и из счётчиков итоговых ошибок.
- `tasks` и `oldest_pending_seconds`: задачи владельца архива и возраст
  ожидания; общая очередь Range также публикует активные и допустимые файлы
  в `gauges`. `first_byte_p95_last_1024` — p95 по последним 1024 непустым
  Range-ответам, без таймаутов.
- `sha_processing_seconds` / `range_processing_seconds` и соответствующие
  `*_queue_seconds`: время работы фоновых задач и ожидания перед их запуском.
  Это сумма времени файлов, включая прерванные задачи; при параллельной работе
  она может превышать длительность окна. Работа включает ожидание сети,
  лимитов и запись блоков, но не ожидание в очереди. Значения обновляются
  после завершения или корректной остановки задачи.
- В `DEST/.download/tasks/*.json` поле `timing` хранит накопленные
  `processing_seconds`, `queue_seconds` и число запусков `runs` для конкретного
  файла SHA/Range. Ожидание включает паузы между запусками сервиса. Измерения
  начинаются с `coverage_since`; старое время не восстанавливается. При
  аварийном завершении незамеренному запуску соответствует
  `unmeasured_interrupts`, а не выдуманная длительность. Эти поля не измеряют
  обычную передачу aria2.
- `range_eof_retry_details`: фактические HTTP-повторы сразу после EOF,
  с путём и SHA файла, границами `start` / `end` (конец не включён),
  номером HTTP-попытки в логическом Range-запросе `attempt`, новыми
  `accepted_bytes`, длительностью запроса и результатом `error`.
  `previous_eof_bytes` — байты ответа, который оборвался перед этим повтором.
  Это уже принятые по HTTP-разметке байты, ещё не подтверждение записи на диск
  или SHA; сохранённый объём учитывает `range_received_bytes`.
  Нулевые результаты тоже сохраняются. Счётчики `range_eof_retry_attempts`,
  `range_eof_retry_useful_attempts`, `range_eof_retry_accepted_bytes` и
  `range_eof_retry_request_seconds` позволяют оценить пользу повторов.
  Детали поступают через буфер памяти на 1024 записи; при переполнении
  старые детали вытесняются, их число видно в `range_eof_retry_buffer_overwrites`.
  Вытесненная запись могла уже попасть в текущий срез; накопительные счётчики
  сохраняются независимо от буфера. После ошибки записи детали могут
  повториться в JSONL: уникальный ключ — `run_id` + `sequence`.
  EOF при чтении тела Range-ответа больше не получает немедленных повторов;
  новые записи здесь относятся к обрывам до получения тела. Старые срезы
  сохраняют статистику прежней политики.
- `host_rates`: байты/с физических сетевых интерфейсов, чтение/запись
  диска назначения (`gauges.disk_device`), занятые миллисекунды диска/с и CPU процесса в секундах/с.
  Умножьте `rx_bytes:ИНТЕРФЕЙС` на 8/1e6 для Мбит/с, `disk_busy_ms` делите
  на 10 для процентов. Это общая нагрузка машины; её нельзя складывать
  между сервисами или приписывать одному загрузчику. CPU не включает aria2.
  Для Btrfs устройство определяется через mountinfo; в многодисковой Btrfs
  конфигурации это только устройство, указанное точкой монтирования.

Видеофайлы для метрик не читаются: используются результаты задач, только
новые строки aria2 и небольшие `.aria2` bitmap. URL, токены и полные строки
ошибок в статистику не копируются. Ошибка записи метрик выдаёт предупреждение,
но не останавливает скачивание. `.download` и метрики не публикуются в Git.

```sh
tail -f "$DEST/.download/metrics.jsonl"
python3 -m json.tool "$DEST/.download/metrics-latest.json"
```

aria2 использует IPv4 (`--disable-ipv6=true`): в текущей сети нет маршрута IPv6.
Готовые SHA/Range-результаты применяются пакетами до 64 файлов. Общие журналы
сохраняются до отметки задач `applied`; незавершённый пакет повторно применяется
после перезапуска без повторного скачивания подтверждённых блоков.

Отдельных TCP-проб нет: решение о повторе принимается по настоящему запросу.
`EHOSTUNREACH`, `ENETUNREACH`, `ENETDOWN` и временная ошибка DNS повторяют
исходный запрос без расходования попыток файла. Первая пауза — 0 секунд,
затем 0,1 → 0,2 → 0,4 → 0,8 → 1,6 → 3,2 → 5 секунд. Все повторы Range
проходят через общий лимит запросов. Ожидание прерывается при остановке.

Таймаут и сброс соединения неоднозначны. Range делает до двух
подтверждающих повторов, сохраняя принятый префикс и запрашивая только остаток.
EOF при чтении тела ответа (`Incomplete response`, `IncompleteRead`,
`SSLEOFError`, `RemoteDisconnected`) не получает немедленного повтора:
принятые байты сохраняются, недостающие участки исследуются меньшими
диапазонами в следующих проходах. Обрыв до чтения тела остаётся сетевым
сбоем с ограниченными подтверждающими повторами.
Если за последние 30 секунд в том же процессе ошиблись минимум три разных
ресурса при установлении соединения (или на неизвестном этапе) и после
начала этих сбоев не было успешной передачи или HTTP-ответа,
повторы продолжаются без списания попытки файла. Повторяющиеся обрывы тела
ответа сами по себе не включают бесконечные сетевые ретраи: после
подтверждающих попыток обычная загрузка переходит к проверке и Range.
Успешные реальные запросы
снимают это предположение; явные ошибки маршрута продолжают повторяться
даже при успехах других файлов. История ограничена 256 ресурсами и не
сохраняется между запусками. Это эвристика: один недоступный узел и общий
сетевой сбой не всегда можно различить по таймаутам.

HTTP-ошибки сохраняют ограниченные повторы; для 429/503 учитывается
`Retry-After` для запросов API и Range. Метаданные используют существующие пять попыток, без
дополнительных подтверждающих запросов. Повтор aria2 читает только новые
полные цепочки ошибок текущего запуска из `aria2.log` и исключает файлы,
завершённые в этой партии; для незавершённых ресурсов берётся последняя причина.
Успехи и ошибки учитываются в порядке событий лога.
После отправки HTTP-запроса таймаут ожидания заголовков не считается
доказательством общего сетевого сбоя: две подтверждающие попытки, затем
обычные повторы файла и SHA/Range с сохранением частичных данных. Этап
определяется по CUID в журнале aria2; метрики на решение не влияют.
Явные ошибки маршрута и коррелированные сбои подключения сохраняют
сетевые повторы без расходования попыток файла.
Git push использует причину из stderr. HTTP/HTTPS проверяют все адреса:
ошибка маршрута IPv6 не скрывает таймаут или отказ соединения IPv4.
Проверка сертификатов HTTPS остаётся штатной. TLS EOF считается
неоднозначным сбоем; ошибка проверки сертификата не получает сетевые ретраи.
При 401/403 Range обновляет ссылку и повторяет оставшийся диапазон даже
на последнем проходе: максимум одно обновление метаданных на проход и
один повтор ссылки на запрос. Параллельные диапазоны используют общее
обновление, а SHA-256 и размер источника проверяются перед продолжением.
`REQUEST RETRY` сообщает категорию, этап сбоя, errno, HTTP-код и паузу,
без URL или токенов. Строки повторов ограничены одной на 30 секунд для
одной операции. В `range_attempts[].ranges[]` сохраняются `request_attempts`,
`retry_reasons`, `request_errors` и `last_failure`; метрики содержат
`range_http_attempts`, `range_retries_*` и `errors.range_causes`.

### Ожидание внешнего диска

Для автоматического возобновления после отключения запускайте очередь или
Range-worker через `storage.py`. UUID берётся у файловой системы; после
повторного подключения допускается другая точка монтирования того же диска.

```sh
python3 storage.py --uuid DISK_UUID --mount-root /run/media/user/DISK_UUID \
  --log-file "$HOME/.local/state/yds-download/courses.log" -- \
  python3 semester_queue.py /run/media/user/DISK_UUID/YandexDisk/.download/semester-queue/queue.json
```

При отключении, ошибках I/O или режиме только чтения дочерний процесс
останавливается, а очередь сохраняет текущую задачу. Контроллер ждёт тот же
UUID, сверяет устройство до запуска, проверяет запись с `fsync`, обновляет локальные пути при смене точки
монтирования и возобновляет работу. `--poll-interval` — 5 секунд по умолчанию,
`--stop-timeout` — 90 секунд; для systemd задайте `TimeoutStopSec=120`.
Журналы JSON/JSONL, проверенные SHA тела и опубликованные копии синхронизируются с диском перед
публикацией завершения. При ошибках диска CLI возвращает 75, а не ошибку файла.

На системном диске хранятся только служебная блокировка/карта монтирования
(`--state-dir`, по умолчанию `~/.local/state/yds-download`) и ротируемый лог:
4 МиБ × 3 файла на сервис, около 36 МиБ для трёх сервисов. При остатке
меньше 512 МиБ логирование прекращается. Видео и основное состояние
`.download` остаются на внешнем диске. Вне `storage.py` автоматического
ожидания и поиска нового монтирования нет.

### Общий каталог Nextcloud и папка приёма

Для очереди курсов можно пропускать оригиналы, уже доступные в публичном
каталоге Nextcloud:

```sh
python3 semester_queue.py /data/.download/semester-queue/queue.json \
  --defer-range --nextcloud-existing 'https://cloud.example/index.php/s/READ_TOKEN?dir=/'
```

Этот же `--nextcloud-existing URL` поддерживает `download.py download`.
Проверяются семестр, папка курса, исходное имя без префикса `001 - ` и
размер. Для пропуска файла нужна **совпадающая SHA-256 в WebDAV** либо
сохранённое подтверждение нашей собственной загрузки: полный SHA-256
отправленного тела, HTTP 201 от Nextcloud и соответствие исходному файлу.
Если WebDAV не публикует SHA-256, одно совпадение имени и размера **не**
считается доказательством целостности: исходник не пропускается. Новый
противоречащий SHA-256 или размер отменяет доверие к старой квитанции.
Квитанция подтверждает отправку, но не является независимым повторным
скачиванием и хешированием серверного файла. Подтверждение успешной отправки не истекает: отсутствие файла в общей
папке не запускает повторную загрузку. Если текущая сессия оказалась дублем,
отправитель восстанавливает подтверждение из журнала по тому же ключу файла.
Противоречащие данные WebDAV (размер или SHA-256) по-прежнему запрещают
считать такую удалённую копию доступной. Для намеренной повторной отправки
нужно явно удалить запись файла из `nextcloud-uploads.json` и его успешные
записи из `nextcloud-uploads.jsonl`, предварительно остановив отправитель.
Доступные таким образом
удалённые копии учитываются в `remote_available`, отдельно от `verified`;
они не становятся локальными SHA-доказательствами и не добавляют владельца
в Markdown. `--deep` проверяет
локальные файлы и не совмещается с этим флагом. При повторном запуске архивы
с удалёнными копиями проверяются заново, в том числе после отключения флага.

Для локальной копии используйте резервный источник вместо пропуска:

```sh
python3 semester_queue.py /data/.download/semester-queue/queue.json \
  --defer-range --nextcloud-fallback 'https://cloud.example/index.php/s/READ_TOKEN?dir=/'
python3 range_queue.py --queue /data/.download/semester-queue/queue.json \
  --nextcloud-fallback 'https://cloud.example/index.php/s/READ_TOKEN?dir=/'
```

`download.py download` также принимает `--nextcloud-fallback URL`. Яндекс
остаётся первым источником; после обычных попыток скачивания Nextcloud
проверяется перед восстановлением Range. Worker с этим флагом обрабатывает
также ранее завершённые неудачные Range-задачи; старые сохранённые пометки
удалённого пропуска при этом не заменяют локальное скачивание. Уже законченный поиск
диапазонов при такой проверке заново не запускается. Личные/root-каталоги
и частичные удалённые копии исключены. Флаг нельзя совмещать с
`--nextcloud-existing` или проверкой `--deep`.

Кандидат должен совпадать по семестру, курсу и исходному имени. Его размер
и опубликованный SHA не заменяют проверку: скачанное тело целиком сравнивается
с SHA-256 Яндекса. Совпавшая копия сохраняется как локальный оригинал и
попадает в обычные отчёты. Другая копия сохраняется рядом с суффиксом
`(SHA mismatch, cloud.example)`; её фактический SHA записывается отдельно,
а проверенным оригиналом она не считается. Хеш в имени различает несколько
альтернативных копий. Если кандидатов несколько, проверяются остальные,
включая случай ошибки первого файла. Существующие файлы не перезаписываются.

Метаданные каждой попытки и незавершённые тела лежат на диске архива в
`.download/nextcloud-downloads/`; история — `.download/nextcloud-downloads.jsonl`.
Обрыв возобновляется только при сильном ETag и правильном Content-Range;
если сервер вернул полное тело, запись начинается заново. Ошибка повторяется
не раньше чем через минуту, отсутствие кандидата — через час. После сохранения
проверенного оригинала или копии с другим SHA повторная отправка GET не нужна,
пока локальный файл не изменился. Параллельно допускаются две резервные
передачи на процесс; лимит Range для Яндекса сохраняется. Прогресс виден
в логах загрузчика/Range как `NEXTCLOUD DOWNLOAD PROGRESS` и в JSONL.

Загрузка недостающих видео идёт отдельным процессом, параллельно загрузчику
и Range. Он обрабатывает все включённые архивы очереди, включая уже законченные:

```sh
python3 nextcloud.py --queue /data/.download/semester-queue/queue.json \
  --nextcloud-existing 'https://cloud.example/index.php/s/READ_TOKEN?dir=/' \
  --nextcloud-upload 'https://cloud.example/index.php/s/DROP_TOKEN' --nickname Walterit
```

Для одного архива: `--destination /data/ШАД-осень-2023` вместо `--queue`.
`--transfers` задаёт число одновременно отправляемых файлов (по умолчанию 4).
Для автоматического подбора в пределах 1–8 добавьте
`--auto-transfers --min-transfers 1 --transfers 8`. Начальное число — минимум;
каждые 90 секунд полностью занятых слотов сравнивается скорость подтверждённых
блоков. Добавленный слот сохраняется при приросте не меньше 10%; пробное
уменьшение сохраняется при потере не больше 10%. Неудачная проба откатывается,
следующая начинается не раньше чем через 5 минут. Проверяются оба направления;
на границе диапазона тоже выдерживается пауза. При снижении лимита активные
файлы продолжают отправку, новые ждут освобождения слотов; скорость оставшихся
файлов обновляет контрольный замер для пробы уменьшения. Если работы меньше
лимита, незавершённая проба отменяется и после простоя собирается свежий замер.
Неподтверждённые попытки и уже сохранённый до запуска прогресс
не добавляют байты в измеритель. Решения и скорость в Мбит/с видны в логе
по строкам `NEXTCLOUD CONCURRENCY`. Это поиск по текущим измерениям, без
гарантии максимума при меняющейся скорости сервера/сети и без тестовых запросов.
Внутри файла блоки отправляются последовательно; начатые файлы получают
свободные слоты раньше новых. Изменения журнала объединяются под блокировкой,
чтобы завершение одного файла не стирало прогресс другого.
`--once` обрабатывает текущие доступные копии один раз; без него процесс
повторяет проверку каждые 30 секунд (`--poll-interval`). `--timeout` — таймаут
сокета WebDAV, по умолчанию 120 секунд. При запуске сервисом используйте
`storage.py` как для остальных очередей: полезные данные остаются на внешнем
диске, лог ротируется, отключение диска приводит к ожиданию и возобновлению.
Запросы Nextcloud учитывают стандартные `HTTPS_PROXY`/`NO_PROXY` окружения.

Чтение каталога по `--nextcloud-existing` повторяется при TLS EOF, таймауте,
обрыве/повреждении XML-ответа и HTTP 429/500/502/503/504: всего три попытки,
паузы 1 и 2 секунды со случайным разбросом ±25%. После исчерпания попыток
ошибка кешируется на 60 секунд, затем следующий запрос этого курса снова
проверяет каталог. Срок ожидания сохраняется между проходами отправителя;
успешные списки в новом проходе обновляются. `Retry-After` учитывается; ожидание больше 5 секунд
откладывает чтение этого каталога, освобождая общую блокировку чтения.
HTTP 401/403 не вызывают немедленных повторов: повторная проверка доступна
через 60 секунд. HTTP 404 считается отсутствием каталога.
Если прочесть список не удалось, отправка без проверки наличия копии не идёт;
обычная загрузка из Яндекса продолжается. Ожидания повторов прерываются
остановкой сервиса. Диагностика: `NEXTCLOUD LOOKUP RETRY` / `LOOKUP DEFERRED`.
Папка приёма не перечисляется: успех отправки определяется подтверждением
сервером и локальной квитанцией, даже если файл ещё не появился в читаемой папке.

Отправляются только видео из манифестов курсов, с действительным локальным
SHA-доказательством либо из `partial-copies.json` с более 50% сохранённых
байтов. Личные/root-каталоги исключены. Путь сохраняет принадлежность:
`2023-fall/Название курса/001 - название.mp4`. Нумерация берётся из полного
списка видео папки, отсортированного по исходным именам; пропущенные файлы
оставляют промежутки в номерах. Частичная копия получает имя
`001 - название (partially available 71.43%).mp4`; это процент байтов, не времени.
Очень длинные имена сокращаются тем же способом, что локальные файлы.

Публичные ссылки без пароля не требуют учётной записи или cookie. Реализация
использует [публичный WebDAV Nextcloud](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/basic.html),
включая обязательный `X-Requested-With: XMLHttpRequest`. Для папки приёма
используются `MKCOL`, `PUT` и `MOVE` публичного API загрузки блоками.
Для запроса файлов передаётся `X-NC-Nickname`: `--nickname` по умолчанию
берётся из `mark` очереди либо равен `yds-download`. Сервер помещает файлы
в папку отправителя: `Walterit/2023-fall/Название курса/...`.

Журнал `.download/nextcloud-uploads.json` синхронизируется с диском перед
отправкой и после ответа сервера. `uploaded` ставится только после HTTP 201,
полной отправки и проверки неизменности файла; SHA-256 считается по потоку,
для оригинала также сверяется с метаданными. В журнале остаются целевой путь,
размер, SHA отправленного тела и подтверждение сервера. Эту запись можно
использовать до появления файла в общем каталоге. Передача идёт блоками
по 16 МиБ (`--chunk-size-mib`, минимум 5) с постоянным ID загрузки и сохранением
номера подтверждённого блока. Повтор блока безопасен; завершение использует
тот же ID. Это предотвращает дубликаты при потере ответа: обычный PUT в папку
приёма автоматически получил бы новое имя. Временные сетевые ошибки повторяются сразу на том же запросе
(два дополнительных повтора с коротким ожиданием; `Retry-After` учитывается).
Ошибки маршрутизации повторяются до восстановления сети или остановки.
При PUT заново передаётся только текущий блок, подтверждённая часть файла
не перечитывается. Если повторы исчерпаны, состояние сохраняется до следующего
обхода. Файлы с подтверждёнными блоками обрабатываются раньше новых во всех
архивах; номера файлов при этом не меняются. Попытки скачивания Яндекса
не расходуются. Остановка и ошибки локального диска прерывают повторы.

После передачи блоков состояние `assembling` сохраняется перед MOVE.
Потерянный ответ повторяет только MOVE; если сервер уже убрал блоки или вернул
конфликт (404/412), ставится `unconfirmed`, а не `uploaded`. Новая копия при
этом не отправляется. Такие записи требуют внимания, если файл долго не
появляется в общем каталоге. Незавершённый блок отправляется заново, остальные
подтверждённые блоки сохраняются. Перед продолжением отправитель проверяет
наличие upload-сессии через PROPFIND: сетевой сбой сохраняет позицию,
подтверждённый HTTP 404 сбрасывает её до создания новой сессии. При истечении
серверной сессии незавершённая передача начинается заново.
Если PUT возвращает именно `412 Missing metadata for chunked upload`,
папка сессии может существовать, хотя сервер уже потерял необходимые
метаданные. Отправитель сохраняет историю старой сессии и начинает этот файл
с новым ID, не удаляя чужие файлы или старую сессию. Это допускается один раз
за обработку файла; повторная потеря метаданных оставляет его в очереди.
Другие HTTP 412 и ошибки завершающего MOVE не сбрасывают передачу.
Сообщение XML-ошибки сервера сохраняется в `error_reason`.
Причина описана в [Nextcloud #61604](https://github.com/nextcloud/server/issues/61604). Контрольные копии на системном диске не создаются.

Наблюдение за отправками:

```sh
tail -f /data/ШАД-осень-2023/.download/nextcloud-uploads.jsonl
```

JSONL пополняется при начале (`uploading`), после каждого подтверждённого блока
и после каждой завершённой попытки: `uploaded` означает
подтверждённую отправку, `pending` — повторяемую ошибку, `unconfirmed` —
неподтверждённое завершение/конфликт. Поля `target`, `sent_bytes`,
`payload_size`, `payload_sha256`, `http_status`, `bytes_percent` показывают,
что именно отправлено. Это журнал истории; последнее состояние хранится
в одноимённом `.json`. Текущая передача пишет `NEXTCLOUD UPLOAD PROGRESS`
с числом байтов в лог раз в 30 секунд. Если отправщик запущен через
`storage.py --log-file .../nextcloud.log`, смотрите `tail -f` этого файла;
через обычный systemd — `journalctl --user -u yds-download-nextcloud -f`.

## OpenCloud: отдельная отправка в общий Space

`opencloud.py` отправляет видео ШАД в проектный Space `ysda-videos`, папку
`ingest/<username>/<год-семестр>/<курс>/`. Личное хранилище и личные архивы
не используются. Наличие копии в Nextcloud не исключает отправку в OpenCloud.
Имена сохраняют числовые префиксы. Приоритет — оригинал с проверенным SHA-256;
при отсутствии оригинала доступны восстановленные копии с более чем 50% байтов
и зарегистрированные OBS/CamRip. Для них сохраняются явные суффиксы
`(partially available XX%)` и `(CamRip, completeness unverified)`.
CamRip берётся из `.download/recordings.json`, при наличии соответствующего
исходного файла в манифесте. Непривязанные записи экрана не отправляются.

По умолчанию команда только показывает локальных кандидатов: сетевых запросов
и отправки нет. Для фактической отправки нужен явный `--upload`.
Команда делает один обход, не устанавливает и не запускает сервис.
`--transfers N` задаёт число одновременных отправок (по умолчанию 1).
Для фонового режима добавьте `--upload --transfers 2 --poll-interval 300`:
после завершения прохода команда ждёт 300 секунд, обновляет каталог Space
и ищет новые локальные видео. Запросов на каждый файл ради проверки наличия нет:
используется один снимок каталога на проход и ответы сервера при публикации.
Обычный запуск без этих флагов по-прежнему ничего не отправляет.
Оба отправителя удерживают отдельные блокировки каждого своего архива до
завершения процесса. Новые архивы допускаются в работу только после захвата
блокировки; занятый новым конкурирующим запуском архив откладывается до
следующего прохода. Nextcloud и OpenCloud используют разные блокировки,
поэтому могут отправлять один архив одновременно независимо друг от друга.

Для автоматической параллельности нескольких облаков передайте обоим
отправителям одинаковые параметры:
`--upload-budget "$HOME/.local/state/yds-download/upload-budget" --min-transfers 2 --transfers 8`.
Это один общий диапазон **2–8 файлов**, а не восемь файлов на каждое облако.
Отдельный `--auto-transfers` при этом не нужен. Без `--upload-budget`
прежние режимы и фиксированные лимиты сохраняются.

Контроллер сравнивает суммарную скорость подтверждённых сервером новых байтов
за 90 секунд, пробует изменить общий лимит на один файл и откатывает пробу,
если увеличение не даёт 10% прироста. Начатые файлы не прерываются: уменьшение
лимита запрещает новые отправки до освобождения слотов. Для ожидающего облака
без активных файлов резервируется свободный слот. Закрытие или падение
процесса освобождает его слоты; при несовпадении настроек участников запуск
завершается с ошибкой. Сохранённые до запуска блоки не увеличивают счётчик скорости.

Текущее состояние — `upload-budget/state.json`: `controller.limit`,
`controller.last_rate` (байт/с последнего замера), `controller.last_rate_time`
(время этого замера; `time` в корне — обновление состояния), `controller.total`
(подтверждённые байты текущего совместного запуска), `members` с именами облаков,
числом `active`/`waiting` и их `confirmed_bytes`. Файл перезаписывается и не
содержит URL или токенов. Это небольшое состояние можно держать на системном SSD;
видео и состояния их возобновления остаются на диске с архивами.

```bash
# В файле — только App Token из настроек OpenCloud, без кавычек.
chmod 600 ~/.jumpingcrub.apptoken
python3 opencloud.py \
  --queue /data/YandexDisk/.download/semester-queue/queue.json \
  --destination '/data/YandexDisk/ШАД весна 2026' \
  --server https://ysda-recover-dsk.jumpingcrab.com \
  --username Walterit --password-file ~/.jumpingcrub.apptoken

# Ограниченная проверка: максимум два новых видео.
# Добавить к предыдущей команде: --upload --limit 2
# Для ручной отправки всех доступных кандидатов: --upload
```

`--destination` можно повторять, включая архивы вне основной очереди.
Токен читается из файла, не попадает в аргументы процессов, Git и логи.
Сервер должен принимать App Token через Basic Auth; основной пароль аккаунта
может не подходить. TLS проверяется, HTTP-перенаправления не выполняются,
учётные данные передаются только исходному HTTPS-серверу.

Перед отправкой читается весь Space и проверяются контрольные суммы файлов
во всех папках, включая чужие (`starphoenix` и любые другие).
Совпадение имени и размера сразу исключает отправку без чтения удалённого
тела; числовой префикс вида `001 - ` при сравнении имени убирается.
Это разрешённая эвристика, а не доказательство целостности удалённой копии.
Если доступен общий хеш, используется он; противоречащий известный хеш
не заменяется эвристикой имени и размера. Имя и размер не требуются для
совпадения известных контрольных сумм.
Переименованные копии исключаются по контрольным суммам из метаданных:
локальный SHA-1 сравнивается с удалённым SHA-1 без скачивания видео.
Общий MD5 из метаданных Яндекса и OpenCloud позволяет вообще не читать
тела файлов. Новые манифесты сохраняют MD5 вместе с SHA-256; для старого
манифеста он запрашивается только при наличии подходящей по размеру копии
с MD5 и кешируется в `.download/opencloud-source-hashes/`. Ответ Яндекса
должен подтвердить исходные размер и SHA-256, иначе его MD5 не используется.
Если нет общего хеша и совпадения имени с размером, копия не считается
дубликатом. Проверка дубликатов не скачивает удалённые видео.
Существующие файлы не перезаписываются:
загрузка идёт во временное имя внутри своей папки и публикуется через
WebDAV MOVE с `Overwrite: F` после проверки размера и контрольной суммы.

Используется [TUS OpenCloud](https://docs.opencloud.eu/docs/dev/server/apis/http/tus_upload/):
после обрыва или рестарта HEAD сообщает подтверждённое смещение, PATCH
продолжает с него, включая данные, принятые сервером перед потерей ответа.
Между успешными PATCH используется уже подтверждённое смещение; повторный
HEAD нужен только при возобновлении или после ошибки.
Сначала продолжаются уже начатые сессии. По умолчанию отправляется один файл;
блок — 10 000 000 байтов, `--chunk-size` меняет его размер. `--timeout` —
120 секунд, `--retries` — два повтора с паузой и jitter. При исчезновении
сессии без опубликованного файла состояние сохраняется с ошибкой: автоматического
сброса подтверждённых данных и создания новой сессии нет.

Состояние хранится по каждому видео в `.download/opencloud-uploads/`,
история пополняется после подтверждённых блоков и окончания отправки:

```bash
tail -F '/data/YandexDisk/ШАД весна 2026/.download/opencloud-uploads.jsonl'
```

`sent_bytes` — подтверждённая сервером позиция, `uploaded` — файл проверен
и опубликован; `pending` сохраняет сессию при ошибке. В JSONL нет URL сессий;
приватные файлы состояния находятся в каталоге с правами `0700`.
Тела видео и временные копии на системном диске не создаются. При запуске
на съёмном диске применяйте `storage.py` с UUID так же, как для других команд.

### Proof journal readers and cloud traversal

Upload polling and cloud fallback keep compact incremental SHA/stat proof indexes. Concurrent readers never repair `events.jsonl`: an unfinished final line stays untouched and is retried after the writer appends its newline. Archive owners retain crash-tail repair under the archive lock. Cloud fallback indexes each `(path, local)` copy separately and omits Range attempt histories. OpenCloud uses exact DAV paths for traversal; course matching preserves trailing spaces while normalizing Unicode.

### Slow local aria2 RPC

`--rpc-timeout` defaults to 30 seconds; `--rpc-status-retries` defaults to 2 extra reads. A transient `tellStatus` transport error retries the same GID while retaining its download slot. `addUri` is never replayed after an ambiguous reply. An exited engine, permanent RPC rejection or exhausted retry allowance stops safely with native resume state retained; supervision can resume it. User interruption and disk-full handling retain priority. Startup RPC calls stay within the 15-second readiness deadline. These settings do not change Yandex HTTP timeouts.

Existing foreground metrics collect `aria_rpc_calls`, `aria_rpc_seconds`, `aria_rpc_failures`, `aria_rpc_timeouts` and `aria_rpc_status_retries`; collection observes the actual authenticated control calls and sends no extra probes. Metrics are batched by the existing interval. Calls and failures include readiness polling while the RPC server starts; status retries count only repeated observations of an existing GID.
