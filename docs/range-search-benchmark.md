# Проверка адаптивного Range-поиска

Ветка `perf/adaptive-range-search`, база `9fc2381`. Проверка 12 октября 2026 года на двух corrupted-видео весны 2026.

## Что изменилось

- Крупный проход без единого полученного байта прекращается после превышения `range_failure_limit`; уже начатые запросы завершаются и сохраняются.
- До половины бюджета мелких запросов распределяется по всем оставшимся пропускам, начиная с сохранённого курсора.
- До четверти бюджета используется для расширения найденных участков в обе стороны. Запросы ограничены пропусками; известные неудачные запросы уменьшаются, одинаковые мелкие пробы не повторяются в проходе.
- Оставшийся бюджет используется для линейного поиска. Только этот этап двигает линейный курсор; дальняя проба не означает, что середина проверена.
- Журнал подтверждает только полученные байты. Непроверенные участки остаются `unprobed`; следующие явные `--retry-check` продолжают поиск.

Это ограниченный поиск, а не доказательство отсутствия данных во всех пропусках. Алгоритм допускает несколько доступных островков; размер физических блоков Яндекса неизвестен.

## Методика

Каждая версия начинает с отдельной копии одного исходного sparse-тела и одинакового журнала диапазонов. Состояние действующих загрузчиков не используется для записи. Публичные метаданные проверены по размеру и SHA-256; обе версии каждой пары получают одинаковую свежую ссылку. Для второго файла порядок версий обращён.

Ограничения измерения: 2 прохода, 64 запроса на мелком этапе, 1 Range-поток, 4 запроса/с, таймаут 5 с, без паузы между проходами. Размеры блоков — штатные 16 МиБ / 1 МиБ / 64 КиБ; порог неудач — 32. Обычные загрузчики продолжали работать. Время зависит от состояния Яндекса и фоновой нагрузки, поэтому это сравнение двух файлов, а не общий норматив ускорения.

Для C++ повторно использован завершённый базовый замер с порогом 0: в старом коде первый проход не прерывался, а второй и так был мелким из-за ограничения в 2 прохода. Изменение порога на 32 не меняет план запросов базовой версии для этой пары.

После каждой пары проверены размер/mtime исходного тела и SHA-256 исходного журнала: производственные файлы не изменились. Проверена согласованность полученных диапазонов с сохранённым журналом. Частичные тела не объявляются валидными по SHA-256: полная проверка возможна только после получения всего файла.

## Результаты

| Файл | Версия | Запросов | Время, с | Новые байты, МиБ | Полный SHA-256 |
|---|---|---:|---:|---:|---|
| C++ Network Programming | baseline | 226 | 135.2 | 1.31 | частичная копия |
| C++ Network Programming | adaptive | 97 | 89.6 | 5.50 | частичная копия |
| Haskell — Типы данных | baseline | 13 | 80.6 | 46.30 | совпал |
| Haskell — Типы данных | adaptive | 13 | 197.0 | 46.30 | совпал |

На C++ получено в 4,19 раза больше новых байтов: 97 запросов вместо 226, время меньше на 33,7%. На Haskell обе версии выполняли одинаковые 13 крупных запросов и восстановили файл полностью; адаптивный этап не понадобился. Разницу 197/81 с нельзя приписать изменённому поиску: порядок замеров, сеть, диск и кеш не изолированы. Два файла не доказывают универсальное ускорение.

Копии обоих прогонов сохранены локально в приватном каталоге теста; производственные corrupted и их журналы не изменены. Полные Haskell-копии отдельно перечислены в `verified-copies.json` рядом с сырыми результатами. Эта ветка не развёрнута в работающем сервисе.

## Автоматические проверки

`python3 -m unittest -q`: 85 тестов проходят. Новые проверки покрывают дальний островок, расширение полученных данных, точность sparse-журнала и содержимого, бюджет запросов, продолжение линейного курсора, бюджет из одного запроса, уменьшение известных неудачных запросов и раннее прекращение бесполезного крупного прохода.
